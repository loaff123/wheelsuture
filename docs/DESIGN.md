# WheelSuture: declared wheel-transition rehearsal

Historical design baseline, written 2026-10-03. Some proposed archive features and capacities were intentionally narrowed during implementation. [Supported-profile refinements](SUPPORTED_PROFILE.md) and [bounded qualification](QUALIFICATION.md) are authoritative for 0.1.0a1; [review reports](reviews/) document the executed checks.

## 1. Outcome, audience, and honest niche

For maintainers assembling Python environments from already-chosen wheel files, answer: “After these ordered changes, which retained distributions lose their declared files, what operation caused it, and does this proposed replay restore the declared final set?” Users supply local digest-pinned wheels and installation history, not per-file expectations. WheelSuture itself only reads inputs and writes reports. It never invokes an installer, imports payloads, executes entry points, discovers a live environment, resolves dependencies, downloads packages, or repairs an environment.

The distinctive deliverable is the entire lifecycle: immutable artifact inventory → ordered transition → retained-payload damage → causal evidence → independently verified repair proposal. A generic collision detector is insufficient. Existing [ModuleGuard](https://github.com/ZJU-SEC/ModuleGuard) already performs static installed-module analysis and conflict detection; [check-wheel-contents](https://github.com/jwodder/check-wheel-contents) validates individual wheel contents; [pip check](https://pip.pypa.io/en/stable/cli/pip_check/) checks dependency compatibility. uv has implemented [module-conflict warnings](https://github.com/astral-sh/uv/pull/13437), and pip has an [overwrite-warning proposal](https://github.com/pypa/pip/pull/14249). No invention-of-simulation claim is justified.

A [pip issue](https://github.com/pypa/pip/issues/7282) and a [2026 uv issue](https://github.com/astral-sh/uv/issues/17645) report removal damaging a surviving distribution. Those reports motivate this hypothesis; the independent original-fixture pip gate is the evidence for our supported model. Neither reports nor the gate establish market adoption. Name availability remains provisional and must be rechecked before any repository or registry creation.

### Chosen approach and alternatives

1. **Chosen:** a small explicit installer profile, separate historical ownership and content state, conservative replay, independently checkable evidence. It is useful offline, reproducible, and testable against real pip.
2. A live environment scanner could capture unknown history but would require discovery, external mutations, and much weaker reconstruction; excluded.
3. General pip/uv/concurrent installation emulation would greatly enlarge the semantics and correctness burden; excluded. Additional profiles require their own oracle gates.

## 2. Supported assertion

The exact successful assertion is: “Under profile P, the modeled final installed distribution identities equal the desired set, and every desired tracked payload/signature requirement is satisfied.” This is called `preserved`, never “environment valid,” “safe package,” or “all files valid.” Report every boundary's retained-payload damage even if later operations repair it.

Tracked: regular copied wheel files including copied metadata other than regenerated control files; modeled rewritten-script signatures; generated console/gui entry-point provider signatures. No imports, dependency compatibility, resolution, ABI validity, native execution, application behavior, permissions, executable-bit correctness, directory-presence/import-namespace inference, or authenticity/provenance guarantee.

Initial v1 profile candidate: `pip-26.2.1-cpython-3.12.14-posix-venv-nocompile-v1`, case-sensitive Linux/POSIX virtual environment, sequential successful operations, no other actor or unknown files. The measured v1 adapter is host/controller pip 26.2.1 `--python TARGET` against a venv created with `--without-pip`. Record the interpreter/installer and scheme evidence in the release profile, not dynamically from the machine running WheelSuture. A second pip version observed in a probe is contrast evidence until independently qualified as another named profile. Python 3.11–3.14 library CI is not evidence for those target installer profiles.

Profile flags: controller pip `--isolated --disable-pip-version-check`, a disposable target virtual environment, explicit local wheel arguments, installation `--no-deps --no-index --no-compile`, and `--force-reinstall` only for the explicit reinstall operation; uninstalls are one exact canonical name at a time, `--yes`. No bulk resolver order is predicted. Profile commands use a sanitized environment: only a known official-toolchain PATH, disposable empty HOME, `LC_ALL=C.UTF-8`, `PIP_CONFIG_FILE=/dev/null`, `PYTHONNOUSERSITE=1`, `PYTHONDONTWRITEBYTECODE=1`; no PYTHONPATH/PYTHONHOME or other PIP/PYTHON variables. Cwd is a controlled directory outside wheel payloads. Target venv excludes system site-packages. `--isolated` alone does not disable site/global pip configuration, and host `-I` is not inherited by the `--python` target. These are fixed preconditions, not live discovery. Command success, available disk space, and absence of external mutation are preconditions, not predicted outcomes. Oracle receipts state whether host pip `--python TARGET` or target `python -m pip` was used; do not silently conflate their interpreter behavior.

The profile models an empty *distribution payload layer* over protected interpreter scaffolding, not a physically empty venv. Reject destinations overlapping the profile's interpreter/pip scaffolding: prefix `pyvenv.cfg` and `pip.conf`, bin names matching `python([0-9]+([.][0-9]+)?)?` or `pip([0-9]+([.][0-9]+)?)?`, the site-packages `pip` tree and `pip-*.dist-info`, and site-root import namespaces `sitecustomize` and `usercustomize`: reject those directory trees, exact names, and every basename beginning `sitecustomize.` or `usercustomize.` (including source, bytecode and extension suffixes). Python startup may import these without an explicit fixture import, so banning only `.py` spellings is insufficient. This is a compatibility restriction, not a malware detector.

## 3. Strict plan input

Read `CONTRACTS.md` for exact ID/hash tuples, sorting, cross-field validation, and error precedence. Normative structural contract: [the plan schema](../src/wheelsuture/schemas/plan.schema.json) (JSON Schema 2020-12). Only UTF-8 strict JSON, maximum 8 MiB, no BOM, duplicate keys, NaN/Infinity, comments, floats, unpaired Unicode surrogates, or trailing data. Unknown keys are invalid. IDs are 1–64 ASCII alphanumeric/underscore/hyphen with a leading letter. Object-key order is immaterial; every operation array is ordered. No TOML or YAML.

Required fields: `schema_version: 1`, `profile`, `wheels`, `initial`, `transition`, `desired`. Each wheel has `id`, a manifest-directory-relative local `.whl` path, and lowercase SHA-256. Paths may not be absolute, contain URI syntax, empty/`.`/`..` components, backslashes, controls, or symlink components. Open beneath the plan directory with no-follow traversal; only regular files. Do not claim a hostile-filesystem sandbox; report races or changed inputs as incomplete. Inputs are opened read-only and hashed before inventory and again before final success/verification. An immutable private spool is allowed only if bounded and separately rehashed; no installed environment is read or written.

`initial` is a sequence of installs of currently absent canonical names. `transition` accepts:

- `install`: absent name only; wheel ID required
- `remove`: exact active wheel ID required; missing or stale artifact is an invalid plan
- `reinstall`: exact active wheel ID required; models uninstall followed by install of that artifact
- `replace`: `from` exact active wheel, `to` different digest of same normalized name; remove old then install new, regardless of version ordering

All operation IDs are globally unique across initial/transition. Wheel IDs and paths are unique; repeated SHA-256 under aliases is invalid to simplify canonical identity. All references must resolve. At most one active artifact per normalized distribution name. Desired wheel IDs are unique by canonical name and mean the **exact** final set, not a subset. Empty desired and transition arrays are allowed. The final active set may differ from desired; this is a demonstrated postcondition failure, not malformed input.

Validate names through `packaging.utils.canonicalize_name(validate=True)` and wheel filenames via `parse_wheel_filename`; parse metadata versions with `packaging.version.Version`. METADATA Name/Version, wheel filename, and the unique top-level dist-info stem must agree under canonical name and version equality. Preserve original spelling for display and actual path mapping; compare identities canonically. A wheel file's build tag is part of artifact identity but not project version. Resolve older unnormalized dist-info spellings only when unambiguous and profile-tested; otherwise `unsupported_layout`, never silently relabel paths. V1 accepts Wheel-Version exactly 1.0, purelib true/false, and filename/WHEEL tags whose expanded set agrees and includes `py3-none-any`. Native/target-specific tags are unsupported in v1 even though arbitrary nonexecuted data bytes are permitted. No “all wheels” claim. These validation choices intentionally reject some installable wheels; unsupported is neither corrupted nor malicious.

## 4. Inventory and destination model

Use a bounded ZIP central-directory preflight before constructing an unbounded `ZipFile.infolist()`. Validate EOCD/ZIP64 bounds, reject multi-disk and encrypted archives, cap entry count and directory bytes before allocation, then stream members in chunks no larger than 64 KiB. Support stored and deflate only initially. Decode ZIP member names exactly as Python 3.12 ZipFile: UTF-8 when bit 11 is set, otherwise CP437. Check raw central/local names for NUL before ZipInfo can truncate them; require the raw names and relevant flags to agree. Reject Unicode-path extra fields and unknown extra-field types in v1; permit only well-formed ZIP64, extended timestamp, NTFS timestamp and Unix UID/GID fields that do not reinterpret paths. Validate all duplicated sizes/CRCs and bit-3 data descriptors against the complete stream and central values; reject contradictory ZIP64 sentinels/records, duplicate extra-field IDs, prepended executable stubs and unexplained trailing bytes. Central and local header names/methods must agree; compressed extents must lie inside the archive and must not overlap each other or directory structures. A repeated shared compressed stream is invalid, even if labels differ. Validate CRC, actual decoded count, declared size, and supported SHA-256/384/512 RECORD digest. For deflate, meter raw decompressor output independently of the declared file_size, require an end-of-stream marker and complete compressed-extent consumption, and reject truncated/trailing/concatenated streams and size contradictions. `ZipExtFile` may truncate output at the claimed size and is not sufficient to prove these properties; the low-level streaming adapter must enforce them before the higher-level reader is trusted. Do not trust claimed sizes to enforce budgets. Fail closed on truncated data, unsupported compression or hashing, duplicate raw/canonical names, file/directory-prefix conflicts inside one wheel, symlinks, hardlink encodings, devices, FIFOs, or unknown file kinds. Never extract to installation destinations and never execute a member.

Paths: case-sensitive, slash-separated, exact Unicode codepoint equality; no Unicode normalization. Maximum 1,024 UTF-8 bytes/path and 255 bytes/component. Reject absolute/drive/UNC forms, `\\`, controls, empty/`.`/`..` components and NUL. Explicit directory entries are structural only, permitted only if regular-directory type and zero payload; they create no persistent ownership claim. A file cannot also be an ancestor directory. Unsupported path names are incomplete analysis, not benign omission.

RECORD is strict UTF-8 CSV with exactly three fields/row, unique paths, decimal nonnegative byte counts, no directory rows, and one empty-hash/empty-size self row. Every other regular member must have exactly one correctly sized/digested row; no phantom rows. Deprecated signature members are unsupported v1 rather than silently accepted. METADATA/WHEEL/entry_points text has independent caps. Single required metadata fields cannot be duplicated or have defects. Unknown harmless metadata fields are retained as bytes; malformed structural metadata fails. Reject bundled INSTALLER, REQUESTED, direct_url.json, legacy dist-info `scripts/`, `.pth` anywhere, `.egg-link`, `.pyc`, `.pyo`, or `__pycache__` payloads. Reject editable metadata/layouts; no attempt to decide whether a `.pth` file is benign.

### One symbolic prefix, not disjoint scheme labels

All destinations are prefix-relative component tuples. Root maps through Root-Is-Purelib; `.data/{purelib,platlib,headers,scripts,data}` maps through the fixed profile. Purelib and platlib alias when the profile says they do. Data is the prefix root, so data `lib/python3.12/site-packages/x.py` must collide with root `x.py`. The measured fixed mapping is purelib = platlib = `lib/python3.12/site-packages`, scripts = `bin`, data = the prefix root, and headers = `include/site/python3.12/{canonical_name}`. Headers are distribution-dependent according to the measured venv scheme. No caller-defined schemes in v1. Reject foreign `.data` directories, unknown scheme keys, `.data/scripts` subdirectories, and every duplicate mapped destination within a wheel, even if bytes match. This avoids assuming pip's intra-wheel overwrite order.

Reserve all dist-info destination namespaces for their actual owner. No wheel may write into another wheel's metadata or through `.data` aliases into any metadata/control namespace. Reject every legacy discoverable `.egg-info` or `.egg` destination/tree and any alternate installed-distribution discovery surface, including through `.data` aliases. Apply all forbidden-bytecode, `.pth`, legacy-metadata and scaffold restrictions AFTER mapping to every producer, including generated entry points and controls; raw member screening alone is insufficient. Also reserve directory ancestors of the interpreter scaffolding. Record the complete mapping and its source member in each claim. Ordinary cross-wheel overlap is allowed and is precisely the analyzed phenomenon. Before simulation, reject as `incomplete` every proper file/ancestor-prefix relation across the UNION of all supplied artifact destinations, including generated outputs and all historical versions, whether or not simultaneously active. Pip can leave empty ancestor directories after uninstall, so checking only active payloads is unsound. This conservative global restriction avoids assuming directory/stash cleanup. Final desired prefix conflicts may additionally carry a concrete unsatisfiable witness. Include protected scaffold files/directories in this structural preflight, rejecting payload files at scaffold directories or payload descendants below scaffold files.

### Content signatures

1. `bytes`: SHA-256 plus length of copied source bytes. Two such requirements are equal iff both fields match.
2. `rewritten_script`: `.data/scripts` first line begins with `#!python` under the pinned pip rule; token contains the SHA-256 and length of bytes after its first LF, and the fixed interpreter/profile token. The original shebang bytes are not asserted installed bytes. Hash the remainder without buffering a potentially huge first line. Equivalent tokens mean the same declared transformed content under this profile.
3. `entry_point`: group console/gui, destination basename, parsed module and attribute, and profile. Distribution/wheel ownership is provenance, not part of equality: two wheels requiring the same target may share a provider signature. This asserts declaration identity and presence, not wrapper bytes or callable validity. The v1 supported grammar is ASCII Python dotted identifiers for module/attribute, mandatory attribute, no extras, no duplicate keys/groups, no continuation ambiguity. Entry-point basenames must match `^[A-Za-z0-9][A-Za-z0-9_.-]{0,254}$` and pass every post-mapping namespace/bytecode/scaffold restriction. Unknown groups remain copied metadata only. Reject special `pip`/`easy_install` wrapper names and console/gui name overlap; reject legacy `.data/scripts` wrapper aliases that pip filters (`name`, `name.exe`, `name-script.py`, `name.pya`). Add those shapes only after their exact RECORD deletion semantics are modeled and oracle-tested.

A bytes signature versus a generated signature at the same destination has **unknown compatibility**. Different typed signatures do not prove different installed bytes. Never label that pair impossible merely because tokens differ. Different byte hashes or different rewritten-tail bytes are proved incompatible content requirements under the pinned transform. Different declared entry-point targets are, at most, a `declared_provider` policy distinction, not a proof of unequal wrapper bytes or impossible runtime behavior. Group-only console/gui differences are unknown unless the profile proves equivalent or incompatible concrete requirements. V1 returns unknown for all unequal generated-provider tokens; it must never present token inequality as byte inequality. Cross-kind uncertain overlap makes preservation/repair `incomplete` unless a later supported operation removes the ambiguity before any required boundary claim is asserted; v1 rejects every such cross-kind overlap across supplied artifacts as unsupported, even if later removed. Do not leave this as an implementation-dependent choice.

### Generated bookkeeping and bytecode

Installed RECORD, INSTALLER, REQUESTED, and direct_url.json are regenerated bookkeeping, not copied-payload correctness claims. Track their presence/removal privately as `control` slots, isolated in the owner's metadata namespace, with no exact-byte claim. Generated RECORD's deletion set is reconstructed from the inventory + profile, not treated as equal to wheel RECORD. Their paths appear in operation evidence as `control_write/control_delete` with clearly typed signatures. No output may say these bytes were verified. Their model identity and deletion footprint remain checkable. Under `--no-compile`, an initially empty payload layer, and no imports, no payload bytecode is created; existing or wheel-supplied bytecode is unsupported. Pip's additional bytecode deletions are excluded by the profile's globally absent-bytecode restriction. Do not emit fabricated bytecode-path events: all possible bytecode destinations are outside the supported occupied domain, including generated destinations. This policy never extends to an unknown live environment.

The [wheel format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) defines destination spreading, script handling, and archive RECORD; [installed-project records](https://packaging.python.org/en/latest/specifications/recording-installed-packages/) describe installed paths and removal bookkeeping. Exact pip behavior is pinned by source receipts and real observations rather than inferred to hold for every conforming installer.

## 5. State, reducer, and causality

Immutable wheel inventory `C[w]` maps destination to claim/signature and provenance. `R[w]` is that installation's declared deletion footprint, including generated controls. State consists of:

- `I`: normalized distribution name → exact active wheel ID
- `H`: historical active claims, keyed by distribution and destination; one wheel's overwrite never edits another wheel's claims
- `A`: actual modeled destination → last written signature/source/event
- tombstones: last deleting operation/event per absent path

`install` writes every mapped payload/provider/control and adds its installed identity; `remove` deletes every R path regardless of other owners and removes only that distribution's identity/claims. A delete of an already missing path is a recorded no-op; it updates the per-path event chain but never replaces the effective deletion cause/tombstone. Only an actual present-to-absent deletion sets the missing-file cause, and a subsequent write clears it. `replace` performs old removal then new installation as one user operation; `reinstall` likewise. Within each expansion emit deletion events first then writes, each ordered by destination bytes. Since supported intra-wheel writes are unique, sorting is behaviorally harmless. Operations are evaluated only at successful user-operation boundaries; subphase evidence remains visible, but transient absence inside one reinstall is not a new user-boundary finding.

At each boundary evaluate all active claims, with `retained` defined as canonical names present before and after that boundary. Missing and displaced retained claims are separate from same-name replaced distributions' old requirements, which are no longer required. Setup can already be damaged; report findings with `phase: initial` and do not attribute them to a later removal. Final desired identity mismatches are distinct findings. Maintain incremental reverse ownership indexes, not quadratic rescans after each event; full independent verification may use a slower bounded implementation.

Every cause contains affected wheel/claim/path, expectation, observation (including absent), the last write/delete event, operation ID/phase, and prior event link. Retain identical-overlap observations, so the explanation can say the second install did not change bytes, but its later uninstall removed a still-required path. Findings use stable IDs. Do not reduce history to one “owner” per path.

IDs are SHA-256 domain-separated hashes over canonical JSON tuples: input manifest semantic digest; case = profile revision + input digest + ordered wheel digests; path = profile revision + destination; claim = profile revision + wheel digest + member/origin + path + signature; operation = case + phase/index + original ID + complete operation; event = operation + event ordinal + path + action + before/after; finding = case + boundary + kind + sorted claim IDs + causal event. Inventory path/claim IDs are case-independent so `inventory_wheel` and single-wheel `inspect` need no plan context; operation/event/finding IDs are case-specific. These are consistency IDs, not signatures or authenticity proofs. JSON canonicalization is UTF-8, sorted keys, separators comma/colon, integers only, exact strings, no floats; logical operation order is retained. Display names never serve as IDs.

## 6. Conservative repair and proof obligation

A repair is a proposal file only. It is never executed, and cannot assert a real unknown environment matches the declared history. Inspect the full desired claim set before choosing operations, including currently intact distributions. Return:

- `already_satisfied`: no operations; independently verified exact desired identity set and claims
- `verified`: a supplied or proposed sequence independently reconstructs and satisfies every desired modeled requirement
- `conflict`: a concrete pair of incompatible desired claims or file/directory requirements proves no single modeled final filesystem can satisfy them
- `unknown`: unsupported profile, uncertain cross-kind compatibility, incomplete input, resource exhaustion, or a failed/unproved replay; no impossibility claim

For v1, only unequal copied bytes/rewritten tails and regular-file prefix contradictions justify `conflict`; differing generated provider tokens return `unknown` unless a later profile supplies a disjointness proof. Equal module/attribute/group/profile tokens may be shared; wheel-owner identity is excluded from this equality. V1 default proposal: canonical-name-order **remove every currently active modeled distribution**, then canonical-name-order **install every desired wheel**. This deliberately conservative two-phase replay prevents stale old-version deletion sets from deleting files written earlier in the repair. V1 certificates always emit the two explicit phases without compaction, including remove+install for a single surviving distribution; the UI may explain that pair as a reinstall. `reinstall` and `replace` remain legal original-plan operations, not emitted v1 repair actions. No minimum-cost, minimum-reinstall, or optimality claim. All desired artifacts must already be supplied. Removing modeled names does not authorize deleting unmodeled distributions or interpreter scaffolding; runtime does neither.

Optional later optimization: retain exact-artifact distributions and force-reinstall a desired-set order only if every reinstall deletion footprint is proved contained in its own rewrite domain (apart from private controls), or a separately proved noninterference order exists. Mere digest equality is insufficient when installer deletion metadata includes extras. Not required for v1.

Proof for the default: after all removals, there are no active old distribution deletion operations remaining. Each desired installation writes all of its requirements and only private control slots; subsequent installs cannot erase paths, and compatible overlapping writes agree. By induction after k installations, every claim of the first k desired wheels is satisfied. After all desired installations, the identity map equals desired, and all desired claims hold. The global all-history prefix restriction plus known scaffold and absence of unknown files prevents historical empty-directory/file substitutions in this profile. Desired-only prefix consistency would establish satisfiability but would NOT establish operational reachability. Freeze each installation instance's deletion footprint before any repair removals. The theorem is conditional on total modeled operations, no residual unmanaged obstructions, and no hidden installation deletion side effects. This is complete for finite supported compatible maps under the profile's assumptions; cross-kind unknowns and unmodeled installer behavior remain outside that theorem. A conflict witness proves only the stated model's simultaneous requirements unsatisfiable; it does not prove imports cannot work or package maintainers intended exclusivity.

A repair must be independently replayed from the **original plan's reconstructed final state**, not from a reset empty state or the claimed report state. The original transition findings remain in the report even when repair is verified. JSON repair certificates bind original case/input/profile, exact wheel digests, full action sequence, final-state digest and verifier revision. Never collapse `unknown` to `conflict`.

## 7. Independent evidence verifier

`verify_report(plan, report, repair=None)` opens and rehashes every source, independently parses members/metadata/RECORD, independently maps destinations, and replays the complete initial/transition/repair sequence. It must not import the inventory, reducer, finding generator, or repair implementation; shared JSON schema/constants/packaging normalization are allowed, but mapping and state transitions are separately written. Exhaustive tests and real pip remain necessary because two implementations can share a mistaken specification.

An analysis report is ORIGINAL-PLAN-ONLY: its operations, findings, final state and digest exclude any proposed repair. Repair is a separate document that references the original analysis digest, carries its own complete expanded repair operations/events/final state, and is always replayed from the reconstructed original final state. There is no reverse reference and no circular report/repair hash. Compare the entire canonical report and, when supplied, the entire repair document, not just a selected positive assertion: IDs, claim inventory, operation sequence, events, causes, all findings, coverage exclusions, final identities/state, and proposed repair result. Reject absent operations, fabricated ownership, altered destinations, source-digest mismatch, false preserved status, omitted failures, invented repair success and invalid causal links. Recompute graph roots and counts. Structural schema success is not evidence success. A modified wheel with an honestly updated report still fails against the independently supplied trusted plan digest. A modified plan and report together are a different case, not authenticity the verifier can detect. No cryptographic authenticity claim.

## 8. CLI, API, status, and outputs

Commands:

- `wheelsuture check PLAN --json REPORT [--html HTML]`: required JSON; optional standalone HTML; short terminal summary
- `wheelsuture repair-plan PLAN --output REPAIR [--json REPORT]`: propose and verify, never execute
- `wheelsuture verify PLAN --report REPORT [--repair REPAIR]`: independent validation; concise stdout verdict
- `wheelsuture inspect WHEEL --sha256 DIGEST --profile PROFILE --json INVENTORY`: same bounded inventory and fixed profile
- `wheelsuture profiles --json`: supported exact profiles, evidence revision, coverage/exclusions

Common output option: `--overwrite` explicitly permits replacing existing report/proposal paths. No apply, install, shell-command-runner, network, environment autodetection, alternate schema, or arbitrary installer flags. `--version` and `--help` are offline. All meaningful status is represented in JSON as well as CLI. `check` exit 0 = complete preserved final modeled claims; 1 = complete demonstrated breakage/desired identity mismatch; 2 = invalid plan/archive/digest/JSON/usage; 3 = unsupported/incomplete/resource limit/unknown; 4 = I/O or output publication failure; 5 = evidence verification failure; 70 = internal error. Keyboard interrupt is 130. Successful `repair-plan` exit 0 means already satisfied or independently verified proposal, 1 conflict witness, 3 unknown; original breakage is still reported. `verify` exit 0 means evidence consistent, even if it honestly reports breakage; 5 means evidence false/tampered, 2 malformed trusted plan, 3 incomplete verification. An unsupported analysis never returns 0.

API (immutable dataclasses; no mutable module globals):

- `load_plan(path: Path, *, limits: Limits = DEFAULT_LIMITS) -> Plan`
- `inventory_wheel(source: WheelSource, profile: Profile, budget: Budget) -> WheelInventory`
- `simulate(plan: Plan, inventories: Mapping[WheelId, WheelInventory], *, budget: Budget) -> AnalysisReport`
- `propose_repair(plan: Plan, report: AnalysisReport, inventories: Mapping[WheelId, WheelInventory], *, budget: Budget) -> RepairProposal`
- `verify_report(plan_path: Path, report_path: Path, *, repair_path: Path | None = None, limits: Limits = DEFAULT_LIMITS) -> VerificationResult`

Input-validation and I/O exceptions are typed (`InvalidInput`, `UnsupportedInput`, `LimitExceeded`, `InputChanged`, `OutputError`); valid completed analysis returns a report even when broken. All public calls can be bounded; library consumers cannot raise hard caps, only lower them. `simulate` refuses manually constructed unvalidated inventory tokens; API objects carry immutable case/profile/digest provenance. Verifier reads source files independently regardless of provided objects.

Normative report/repair/error schemas accompany this document. JSON is emitted in the canonical compact encoding defined above plus one LF, deterministic and sorted, with no timestamp, hostname, absolute paths, locale-sensitive text, or nondeterministic timings. Benchmark receipts are separate. Final status/exit describe final desired claims; historical boundary findings remain complete and visible even when explicitly repaired later. Every report/inventory/repair includes its effective limits. Analysis `resource_usage` describes original-plan work only; repair verification has a separate usage object charged from zero against the same or stricter effective limits, including original-state reconstruction and repair expansion. Verification rejects declared counters/limits that do not match independent reconstruction. Maximum member/RECORD/metadata/depth/state-slot counters are high-water marks; wheels/entries/archive bytes/decoded bytes/claims/deletion paths/events/findings/path text/user operations are aggregate unique input or emitted-item counts for that stage. Archive byte accounting counts each unique source once per stage (rehashing it is still performed); byte counters are deterministic quantities, not I/O performance measurements. Input relative paths may be displayed; provide a redaction option in a future version rather than silently breaking evidence. Terminal paths/messages are escaped so newlines, ANSI and bidi characters cannot spoof output; width truncation must retain IDs and full text in JSON.

HTML: no JavaScript, remote assets, forms, external fonts, embedded active source text or runtime network requests. Fixed CSS; escape every string via HTML text/attribute escaping, including filenames, IDs, metadata and `</script>` payloads. Use opaque hash IDs as anchors, never raw filenames in URLs or attributes. No unsafe markdown renderer or click-through `file:`/`javascript:` links. Include profile, limits, excluded claims, status, transitions, causes, and repair status in readable sections. Unknown/invalid statuses are prominent. Large event lists can be omitted from HTML with explicit count and JSON reference, never from canonical JSON silently.

Atomic file contract: refuse outputs that alias an input, another requested output, or a symlink. Serialize/validate all content to private same-directory temporary files first; flush and fsync, then replace each destination with `os.replace`, fsync parent. Each file is atomic; a set of independent paths is **not** a multi-file transaction. JSON is committed last as the authoritative receipt. If another output succeeds but JSON fails, exit 4 and name partial output paths; never report complete success. Existing output replacement requires `--overwrite` (not implicit). Failed analysis may still atomically write a bounded error JSON, but must not overwrite a previous completed report with a syntactically ambiguous fragment. Stdout is summary only; broken pipe yields output failure. A later optional directory bundle could provide whole-bundle atomic publication.

### Canonical digest preimages and length

For every digest use `sha256(ASCII(domain) + NUL + canonical_json(envelope))`, with no newline in the hashed JSON. `state_sha256` uses domain `wheelsuture/state/1` and envelope `{identities, slots}` sorted respectively by canonical name and destination UTF-8 bytes; it excludes the state digest itself. `evidence_sha256` of an analysis uses domain `wheelsuture/report/1` and the entire report with only its top-level evidence digest removed. Repair verification's evidence digest uses domain `wheelsuture/repair/1` and the entire repair document with only `verification.evidence_sha256` removed; it includes original analysis digest, exact repair actions, expanded events, final state, source hashes, limits and verification usage. It never modifies the original report. Hash IDs use their analogous named domains and ordered tuples exactly as listed in §5; original user operation ID and array index are both retained. `input_sha256` uses domain `wheelsuture/plan/1` and the complete strict parsed plan object. No human description text is outside the evidence digest.

`resource_usage.report_bytes` is the final serialized byte length of that document, including final LF and that field itself. Compute with 64-character zero placeholders for all fixed-length digest fields; update the integer length until stable (bounded to ten iterations), then compute real digests, whose width does not change the length. For a repair document, this field lives in verification.resource_usage; unknown/conflict proposals have no verification usage and enforce the output byte cap directly. Member/metadata high-water counters apply to decoded source data, not JSON string character counts. Inventory uses the same length rule. Error documents remain bounded and carry no unverifiable partial-success digest.

## 9. Resource contract and calibration

Proposed hard limits, all fail closed before success: 1,000 unique wheels; 100,000 total ZIP entries (including explicit dirs); 4 GiB aggregate **actual decoded** bytes; 256 MiB/member; 2,000,000 total expanded path/control write/delete events across setup, transition and proposed replay; 100,000 total mapped claims including generated outputs and controls; 100,000 deletion paths; 100,000 state slots; and 100,000 findings. Charge these before expansion, not merely when serializing. Also: 4 GiB aggregate archive bytes; 32 MiB central directory; 16 MiB aggregate path text; 8 MiB plan; 16 MiB RECORD/member; 2 MiB METADATA/WHEEL/entry_points each; 10,000 user operations in initial plus transition combined; 128 MiB canonical report; nesting depth 32; 1 MiB bounded error report. Integers checked before multiplication/allocation. Limits are global to a run, not reset per wheel/repair/verifier stage without disclosure. Reopening source for independent verification charges a separate explicitly reported verification budget, with the same caps; it cannot bypass a run's analysis limits.

Central directory counts are preflighted before allocation; aggregate decoded counters are charged for actual reads even if compressed headers lie. Reading 64-KiB chunks does not by itself bound memory: intern compact paths/digests, spool bounded events/report when needed, avoid per-event full state copies, and budget generated metadata/entrypoint expansion before creating it. Reject overlapping compressed streams before decoding; do not use compression ratio alone as a bomb detector. The tool is a bounded parser, not a security sandbox. OS memory/CPU/time watchdogs in tests are defense-in-depth, not a guarantee for arbitrary files.

These are proposed maximums, **not measured throughput claims**. Release calibration uses original generated fixtures at 1, 10, 100, 1,000 wheels; 10/1,000/10,000/100,000 entries; shared-name and disjoint-name distributions; actual decoded sizes up to 4 GiB; 255/1,024-byte path boundaries; event expansion up to 2M; compressible and incompressible payloads. Run in an explicit 2-vCPU/2-GiB environment with 120-second wall/60-second CPU budgets and peak RSS measurement. If valid maximum inputs exceed budget, lower published limits or optimize before release; do not ship unmeasured permissive caps. Limit+1 tests must stop before over-allocation. Hold out half of seeds and at least three shapes (dense aliases, long paths, many tiny members) from tuning. Report hardware, Python/pip, source/artifact digests, max RSS, time, and bound-trigger location.

## 10. Verification and implementation gates

### Already-scoped first feasibility gate

Original valid `demo_base` and `demo_slim` wheels share identical `shared/__init__.py` plus separate unique members. Real pip: base → slim → remove slim leaves base METADATA/RECORD but shared absent; reinstall base restores exact hash. Independent filesystem and installed-RECORD reading, no fixture imports. Repeat reverse order, different-byte shadowing, incompatible desired owners, disjoint namespace, upgrade omission and mapping/scripts. Keep full commands, both success and failure returns, source wheel hashes, target schemes, snapshots and installer source hashes. This proves a file-operation failure class, not imports.

### Product acceptance gates (not yet run)

1. Inventory unit corpus: minimal valid wheels, metadata normalization, aliases, prefix collisions, malformed/phantom/duplicate RECORD, unsupported algorithms/compression, symlinks, special files, encrypted/multi-disk ZIP, altered headers, truncated members, duplicate ZIP names, overlapping compressed spans, ZIP64 counts, traversal and resource limit+1.

Examiner imports no WheelSuture code. Pin exact pip/Python/profile/flags; do not use arbitrary downloaded package payloads.
3. PyPA `installer` is a second **mapping** oracle, not an uninstall oracle and not evidence pip semantics generalize. 4. Exhaustive tiny ownership universes and independently generated deterministic state-machine tests: zero/one/two/three names; two/three destinations; two byte values; repeated install/remove/replace/reinstall; conflicting and compatible desired subsets; old deletion footprints. 5.
